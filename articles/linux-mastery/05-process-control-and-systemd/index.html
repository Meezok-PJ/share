Module 05: Kernel Architecture, Process Control & Systemd

⚠️
Sandbox Environment Warning
Execute all commands and scripts strictly inside an isolated Virtual Machine sandbox. Never perform bulk permission changes, system removals, or daemon restarts on unbacked host environments.

Inspecting kernel architecture with uname, monitoring processes with ps/htop/pgrep, signal handling (15/9/1), background job control, custom systemd service daemons, and journald log forensics.

1. Kernel & Hardware Inspection with uname

The uname (UNIX Name) command outputs information about kernel release, architecture, and node hostname:

# Print all system information
uname -a

# Print kernel release
uname -r

# Print machine hardware architecture (x86_64 or aarch64)
uname -m
Figure 1: Querying kernel release, hostname, and CPU architecture via uname -a / -n / -m / -p.

2. Process Tree & State Lifecycle

Linux Process State Transitions
1. Running (R)

Process is currently executing on a CPU core or sitting in the run queue ready to execute.

2. Sleeping (S / D)

Interruptible (S) waiting for an event/signal, or Uninterruptible (D) waiting on disk I/O.

3. Stopped (T)

Suspended via job control signal (Ctrl + Z or SIGSTOP 19).

4. Zombie (Z)

Terminated process whose exit code has not yet been read by its parent process.

Figure 2: Inspecting process table fields (PID, %CPU, %MEM, TTY, COMMAND) via ps -u.

3. Process Signals & Job Control

# 1. Graceful shutdown (SIGTERM - Signal 15) - allows app to close connections cleanly
kill -15 <PID>

# 2. Forceful termination (SIGKILL - Signal 9) - kernel immediately destroys process
kill -9 <PID>

# 3. Reload configuration without dropping connections (SIGHUP - Signal 1)
kill -1 <PID>

# 4. Search and kill by process name
pkill -f "worker.py"

Background vs. Foreground Execution

# Launch process in background
python3 background_task.py &

# Run process immune to terminal hangups (nohup)
nohup python3 long_script.py > task.log 2>&1 &

# View active jobs in current shell session
jobs

# Bring background job #1 to foreground
fg %1
Figure 3: Running commands in the background (&), viewing with jobs, and resuming with fg %1.

4. Systemd Service Daemons & Unit Files

Systemd is the default init system across modern Linux. It manages daemon lifecycles through declarative unit configuration files in /etc/systemd/system/.

Figure 5: Systemd service lifecycle management, status checks, and daemon reloading.

Example Custom Unit File (/etc/systemd/system/myapp.service)

[Unit]
Description=Homelab Python Backend API
After=network.target

[Service]
Type=simple
User=meezok
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/python3 /opt/myapp/server.py
Restart=always
RestartSec=5s
Environment=PORT=8080

[Install]
WantedBy=multi-user.target
# Reload systemd manager configuration
sudo systemctl daemon-reload

# Enable on boot and start immediately
sudo systemctl enable --now myapp.service

# Check live status and telemetry
systemctl status myapp.service

5. Journald Log Forensics

# Stream live logs for a specific service in real-time
journalctl -u myapp.service -f

# View logs from current boot only, filtering for error-level messages
journalctl -b -p err..emerg --no-pager

# View logs generated within the last 1 hour
journalctl --since "1 hour ago"
